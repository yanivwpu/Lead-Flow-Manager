## Phase 2A design

AI Brain delegates a shopping turn to a bounded, deterministic commerce action before generic language generation, only for an opted-in channel/workspace with existing Growth Engine and AI Brain entitlements. The action uses the existing Sales Catalog's `purchaseCandidates` and `verifyForPurchase`; it does not duplicate inventory tables, webhook handling, quota protection, billing or messaging. English, Spanish and Hebrew shopping intent/budgets/options are supported; merchant controls and Inbox summary use existing translations and RTL direction.

Only the latest persisted inbound text in the owned conversation can advance shopping. Caller-supplied history and chatbot node configuration cannot authorize variant IDs or customer confirmation. Product/variant choices originate in live catalog results. Exact names/options or bounded option numbers select an existing choice; ambiguous names ask again. Explicit confirmation follows an exact selection. Price/option changes force another confirmation. Quantity requests are bounded and checked against verified stock/policy. Search budgets are compared as exact decimal strings and currency mismatches fail closed; no currency conversion is implied.

Lightweight state lives in `conversations.shopping_state`; controls live in `ai_settings.shopping_assistant`. The additive idempotent migration and startup patch share the same statements. A short conversation row lock acquires a two-minute lease around catalog calls; another transaction rechecks ownership, latest inbound, pause and handoff before committing state/activity. Provider calls do not hold a database transaction open. Expired workers cannot overwrite a newer lease. The bounded consumed-event list plus persisted latest-inbound check prevent replay of old selection turns. Responses replay for at most 60 seconds; sessions expire after 30 minutes. The API excludes internal lease/event/reply fields. No contact is created, including for anonymous Web Chat visitors.

The existing Inbox receives shopping activity and standard `ai_handoff` events. The summary shows recommendations, selected variant and status. AI Brain retains all existing autonomy, hours, consent, channel and send deduplication gates. The builder's reusable **AI Shopping Assistant** action prepares the same state; it has no sender and cannot create checkout. Transient verification failures default to retry/ask-for-help rather than forcing merchants to intervene; merchants may choose automatic handoff. Human/order requests use the existing handoff lifecycle. No new contact enrichment or follow-up sender is introduced.

The initial implementation deliberately uses bounded catalog choices (at most eight variants verified per turn, with the merchant's maximum limiting displayed options). It cannot promise exhaustive comparisons across a large catalog. There is no reservation, shipping promise, discount promise, order lookup or automated payment collection. Unsupported order questions transfer to a person. The assistant does not feed catalog descriptions into a model: they remain untrusted data. Responses use constrained catalog title/variant/price templates and strip links from labels.

## Shopify checkout architecture investigation

Reviewed official documentation on 2026-10-16:

- [Storefront Cart API / cartCreate](https://shopify.dev/docs/api/storefront/latest/mutations/cartCreate) returns the provider's `checkoutUrl` for a Shopify-hosted buyer checkout.
- [Create and update a cart](https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage) describes cart lifecycle and buyer context.
- [Storefront authentication](https://shopify.dev/docs/api/storefront/latest) distinguishes public `X-Shopify-Storefront-Access-Token` from server-side private `Shopify-Storefront-Private-Token`. Server-side private calls should use a trusted buyer IP, not an arbitrary message value or untrusted forwarded header.
- [Storefront access scopes](https://shopify.dev/docs/api/usage/access-scopes): product listing access and Cart read/write are separate from Admin `read_products` / `read_inventory`.
- [Headless channel management](https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/manage-headless-channels) provides token rotation, publishing and channel management.
- [Admin storefrontAccessTokenCreate](https://shopify.dev/docs/api/admin-graphql/latest/mutations/storefrontAccessTokenCreate) delegates the creating app's unauthenticated grants. Existing Admin product-read access alone does not prove this capability.

Choose **Storefront Cart API**, pinned to `2026-10`, with an explicitly approved server-owned Storefront credential. Do not use legacy Checkout API, draft orders, order/payment APIs or construct handle-based checkout URLs. Cart permalinks are an official alternative, but do not provide the same explicit cart validation/lifecycle and are not implemented as a fallback.

Online Store publication from Phase 1B/#90 is necessary for current catalog eligibility but does **not** establish publication to a Headless/app storefront. Before activation, query the actual variant through the chosen Storefront token; null/ineligible variants must fail closed. Storefront contextual price/currency must match the customer's freshly confirmed selection; Admin price alone is insufficient. Checkout responses must have the exact line, quantity, currency and unit price. Only the returned HTTPS checkout URL may be delivered, on the owned shop or an independently verified merchant checkout domain. Never accept redirect hosts from customer input. No credit card details enter WhachatCRM.

6. Approve staging checkout tests and then merchant activation. A successful API response in a password-protected development store does not prove an anonymous visitor can pay. Test in a separate anonymous browser, document the password gate, use Shopify test payments only, and never capture live payments as a development check.

The checkout adapter is preparation for review; no runtime route, credential provisioner or permission change activates it. The current assistant honestly states that checkout assistance is unavailable after confirming a selection. End-to-end payment/anonymous checkout acceptance remains pending approved configuration and staging verification.

## Final review: fast follow-up verification and shared entry point

The original happy-path integration helper reset #90's durable cooldown before each turn, masking a real failure: an immediate selection/confirmation could receive an empty live result and erase choices or trigger handoff. An empty batch also represents source-lease contention, throttling and provider failure; it is not proof that a selected product is unavailable.

Temporary/unverified results now save an explicit `pending` state with the selected catalog IDs, quantity, choices, query, budget and previous conversation step. Pending replies make no new price/stock claim and do not trigger configured automatic handoff. An explicit localized retry reuses the saved operation through the same #90 verifier and durable quota controls. There are no inline provider retries or cached-stock authorization. A changed live price/options still requires confirmation, including after a pending confirmation. Actual verified ineligibility/stock failure retains the existing failure behavior. Cancel, restart and human requests remain available.

Builder and AI Brain call one shared, testable suggestion entry point. Builder prepares state without sending; AI Brain reads the same persisted event. Pending and completed same-event replays do not repeat verification or activity commits. Temporary conversation-lease contention returns a truthful busy/repeat-request response without altering the lease owner's state or claiming the new request has already been saved. The existing AI send guard remains the sole delivery boundary; its stable inbound-message key rejects concurrent duplicate sends.

Regression coverage leaves the real post-discovery cooldown intact, immediately selects a variant, preserves quantity, recovers with retry, re-confirms price changes, injects a Shopify 429 and checks persisted backoff, holds both source and conversation leases, checks repeated Builder/AI preparation and exercises the existing send guard with a local injected sender and PostgreSQL-backed deduplication. No live customer messages or checkout calls are made.

Remaining limitation: recovery is customer/event driven, with explicit retry (or repeating a busy request); this change adds no background resend job and does not promise a completion time while Shopify backoff or leases persist. The inventory batch API does not distinguish every empty-result reason, so missing/unverifiable variants conservatively remain pending rather than being called out of stock. Sessions still expire under the existing 30-minute policy. Checkout remains disabled.
