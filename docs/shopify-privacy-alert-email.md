# Shopify privacy alert email

The existing one-minute privacy worker, PostgreSQL outbox/retry scheduler and Admin → Privacy monitor now use the app's existing `server/email.ts` Resend transport. No separate email service, queue, Railway service or account is needed. The recipient is fixed in code to `support@whachatcrm.com`.

## Exact Railway variables

Set these on the **existing app service** in the intended Railway environment. If a separate privacy cron worker is already in use, give it the same environment's `DATABASE_URL`, alert URL, token and enable flag. Receiver and worker must share that environment's database. Never connect staging to production's database or receiver.

| Variable | Staging | Production |
| --- | --- | --- |
| `DATABASE_URL` | Existing staging PostgreSQL reference | Existing production PostgreSQL reference; do not change for this feature |
| `RESEND_API_KEY` | Existing Resend sending key, authorized for the sender domain; store as a Railway secret | Existing production Resend key; never copy it into source or tests |
| `RESEND_FROM_EMAIL` | `WhachatCRM <noreply@crm.whachatcrm.com>` or another Resend-verified WhachatCRM sender | Same verified sender configuration; the existing default is `WhachatCRM <noreply@crm.whachatcrm.com>` |
| `SHOPIFY_PRIVACY_ALERT_URL` | `https://<existing-staging-app-host>/api/internal/shopify/privacy-alerts` | `https://app.whachatcrm.com/api/internal/shopify/privacy-alerts` when explicitly approved for activation |
| `SHOPIFY_PRIVACY_ALERT_TOKEN` | New independent random base64url secret, 32–256 characters | A **different** independently generated secret, 32–256 characters; shared only by this environment's worker/receiver replicas |
| `SHOPIFY_PRIVACY_ALERT_EMAIL_ENABLED` | Initially `false`; explicitly set `true` only for the staging smoke test and desired staging operation | **Keep `false` (or unset). This PR does not enable production email.** A later operator-approved activation must explicitly set `true` |

Generate each secret locally with `node -e 'console.log(require("node:crypto").randomBytes(32).toString("base64url"))'`, then save it directly in the correct Railway environment's secret variables. Do not put it in source, PR comments, screenshots or logs. Existing `SHOPIFY_API_SECRET`, `SHOPIFY_PRIVACY_REQUEST_KEY` and evidence/adapter variables remain required for their existing privacy responsibilities; they are not email tokens and must not be reused. `APP_URL` does not control the recipient or email content. No new Resend account is required. Verify sender-domain ownership/DNS and sending-key permissions in the existing Resend account.

## Receiver and privacy contract

`POST /api/internal/shopify/privacy-alerts` requires `Authorization: Bearer <token>`, `Content-Type: application/json`, `Idempotency-Key: shopify-privacy-<alert UUID>` and exactly `{ "alertId": "<existing outbox UUID>" }`. The caller cannot choose recipient, sender, subject, HTML, message, operation status, deadline or action. Tokens use timing-safe comparison. Bodies are limited to 1 KiB and extra fields are rejected. The receiver is registered before the general body parser, session routes and response logging; errors are generic. Railway must terminate TLS on the configured HTTPS domain. The worker refuses non-HTTPS URLs, credentials in URLs, query strings, fragments, unexpected paths and redirects.

The receiver loads the trusted outbox/task records, verifies the issue still exists and validates every rendered field. Emails contain only the random operation UUID, allowlisted issue category/status/action and normalized UTC deadline. They contain no merchant addresses, customer identifiers/details, shop domains, credentials, database queries or provider error text. Unsupported providers get a fixed category/action. Access requests require support fulfilment, never automatic deletion. The email points the operator to Admin → Privacy without embedding a merchant or customer link.

## Durable delivery and retry behavior

Migration/startup patch **0106**, after 0104/0105, adds immutable email snapshots, committed send-intent timestamps, confirmed provider acceptance and reconciliation state to the **existing** outbox. It replaces perpetual task/reason uniqueness with uniqueness for unresolved occurrences. Queue reconciliation is serialized in PostgreSQL; unchanged issues do not enqueue again, and a resolved issue may generate a new occurrence if observed again. Resolution must be observed by a worker tick. Migration 0106 is repeat-safe and serialized across startup replicas.

The existing worker leases claims and retries from one minute exponentially, capped at one hour for email. A pinned PostgreSQL session advisory lock serializes receiver calls across replicas. Before any provider request, the receiver durably saves the frozen sender/body inputs and send intent. Resend requests have an eight-second timeout and use `shopify-privacy-<alert UUID>` as their idempotency key. The body and sender remain unchanged across retries, even if configuration/status/deadline changes. Only a successful provider response containing a message ID records acceptance and marks delivery. A receiver or worker timeout after acceptance cannot resend an accepted occurrence: the durable ledger answers replay requests. Alerts remain queued on failure, and provider responses/errors are never stored in the alert or included in emails/logs.

**Provider limitation:** [Resend idempotency keys expire after 24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys). A local database cannot make an unconfirmed remote send exactly-once forever. Definite rejections with no earlier ambiguous attempt retain automatic retries indefinitely. Timeouts, 5xx/409 responses, malformed acknowledgments and process death are conservatively ambiguous: the worker automatically retries the identical key/body for at most **23 hours from the first uncertain send intent**. After that it retains the alert, marks `email_reconciliation_required`, and makes no further provider calls. This is necessary to prevent duplicate emails after provider deduplication expires. It is a deliberate limitation to indefinite automatic retry for ambiguous outcomes, not a delivered state. No new key is generated automatically.

Admin → Privacy shows `pending`, `accepted`, or `reconciliation_required` per active issue. The on-call operator must inspect pending/reconciliation state as well as email. For reconciliation, use the existing Resend account and the immutable operation/category/timestamp to establish whether Resend accepted the send. Only confirmed acceptance with the actual message ID may be recorded as delivered. If authoritative evidence proves **no acceptance**, an authorized operator can clear uncertainty/reconciliation and the send-intent timestamp for that specific occurrence to resume the existing retry schedule. Never clear these fields merely because an email was not seen; absence from an inbox is not proof of non-acceptance. This PR exposes no public reset/complete endpoint and performs no production reconciliation/data changes.

## Staging verification and production readiness

Use the explicitly invoked [staging smoke-test procedure](shopify-privacy-staging-smoke.md) for a synthetic email test with independently verified database identity, process-only activation, replay checks, deployed Admin verification and test-owned cleanup.

Apply/verify 0106 through the existing startup patches or reviewed migration process; inspect Admin → Privacy before enabling email. In staging, configure the existing verified sender/key and an independent alert token, then explicitly enable the flag. Create only a synthetic random-ID operation in the **staging** database. Verify one email to support, unchanged-issue suppression, generic unauthenticated rejection and pending/retry behavior with a simulated provider outage. Revert the flag to `false` if staging email is not intended to remain active. Integration tests use disposable localhost PostgreSQL and mocked Resend; they do not send email or access Railway data.

Required CI: Shopify onboarding, Shopify contact privacy (including the receiver/outbox integration test), and staging database bootstrap. Both Shopify workflows compare TypeScript diagnostics against the exact PR base, because the base already has unrelated TypeScript errors. Production activation remains a separate reviewed operation after CI, migration, sender-domain verification, monitoring ownership and staging smoke-test evidence. No production deployment, merge, variable change or email activation is part of this PR.
