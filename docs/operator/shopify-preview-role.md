## Access decision

The current PR #302 guard explicitly requires SELECT on every public table/view and rejects missing reads, privileged memberships, writes, ownership and RLS. Today's metadata shows **151 relations, zero RLS and zero foreign tables**; the proposed new role does not yet exist.

The scanner would currently query **85 candidate relations**: known identity/privacy tables plus every relation with a contact FK/ID/list or JSON/JSONB column. It hashes complete matching rows using `to_jsonb(t)`, requiring whole-row SELECT on those relations. A fixed contact/history allowlist or column-only grants would miss references or fail these queries. Its `information_schema.columns` discovery is privilege-filtered, so simply reducing grants can also hide candidate references.

A narrower design is possible only with a reviewed change to authoritative catalog discovery, dynamic candidate coverage and the permission guard. It cannot be achieved by granting 85 relations while leaving #302 unchanged. To finish without redesign, the minimum compatible grant is **SELECT on the 151 existing public relations**, with no sequence grant, future-object/default grant, membership, ownership or grant option. It reads other tenants' data internally as required by the complete-reference audit; this is meaningful access and requires explicit DBA approval despite sanitized output. New/missing objects cause the existing guard to fail rather than silently expand the grants.

## DDL qualification — approval blocker if interpreted absolutely

Current database metadata confirms `PUBLIC` grants `TEMP` and CONNECT. PostgreSQL privileges are additive: revoking TEMP from only the new role cannot deny a privilege inherited from PUBLIC. The plan grants **no persistent DDL rights**, but cannot guarantee an absolute ban on temporary-object DDL by the credential holder without changing shared privileges. Defaults such as `default_transaction_read_only=on` are defense in depth, not an immutable denial. Do not revoke PUBLIC privileges, change existing roles, or claim this limitation is eliminated.

PR #302 permits TEMP and still enforces explicit read-only transactions and no mutation code. **NO-GO for provisioning until the DBA/owner approves this precise scope and qualification.** If “no DDL” includes all temporary DDL without exception, this plan cannot satisfy that requirement while preserving current shared access; stop rather than weaken the requirement or broaden this task.

The 24-hour password expiry is a maximum, not permission to retain access for the entire pilot. Record the UTC deadline and named cleanup owner before provisioning. Revoke immediately after the accepted preview/re-preview window; do not automatically extend it or grant future objects. Expiry may not end existing or pooled sessions, so explicit cleanup is required.
