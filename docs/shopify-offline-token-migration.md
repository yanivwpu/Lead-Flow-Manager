## Official contract checked Nov 10, 2026

Sources: [migration guide](https://shopify.dev/docs/apps/build/authentication-authorization/migrate-to-expiring-offline-access-tokens), [access-token reference](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens), [refresh implementation](https://shopify.dev/docs/apps/build/authentication-authorization/implement-token-exchange).

Public apps must migrate before Jan 1, 2027; legacy Admin API requests are rejected beginning Apr 1, 2027. Authorization-code acquisition requests `expiring=1` and validates the entire offline response. Both expirations use returned TTLs, measured conservatively from request start. A refresh returns a replacement refresh token; use the newly committed pair next time. Do not assume the old refresh token is immediately unusable: Shopify permits ambiguous-request recovery until its replacement is used, bounded by its original expiry and the documented first-use limit. Retain the durable old pair on transient/ambiguous failures; retry on a subsequent invocation, without replaying an Admin operation or message.

Direct legacy migration immediately invalidates the old Admin token. A lost initial response can be recovered by repeating the identical exchange with the original token within seven days, until the issued pair is refreshed or a later acquisition retires it. This exception is specific to the initial migration. It is not a rollback strategy or permission for bulk retries.

## Implementation and persistence

- SQL `0119_shopify_offline_tokens.sql` is additive and idempotent. It creates separate Shopify-only tables, foreign keys and cleanup trigger; it does **not** backfill/exchange tokens or touch orders, catalogs, webhooks, billing, integrations, trials, consent, templates or send settings.
- New access+refresh pairs are AES-256-GCM encrypted together with tenant/shop/installation authenticated context and an independent required `SHOPIFY_OFFLINE_TOKEN_KEY`. No fallback key. Runtime app client ID is recorded and checked before use. Both expiry timestamps are queryable; credentials are never copied into generic integration config, sessions or frontend DTOs.
- `users.shopifyAccessToken` remains the compatible connection/CAS field: legacy rows are unchanged; new installations contain a random opaque reference, stable through refresh. This preserves billing and catalog installation fences without plaintext new credentials. Reauthorization creates a new reference, invalidating stale workers. Existing reference-based maintenance scripts fail closed rather than sending a reference to Shopify. Historical reassignment SQL is unsuitable for migrated pairs: do not run it; a separately reviewed transfer must re-encrypt under the new owner and preserve privacy fences.
- Acquisition checks encryption/storage/cleanup readiness before consuming an OAuth code. Its user connection update and encrypted pair commit atomically. A failed write leaves the previous persisted installation and entitlements unchanged. A consumed authorization code cannot be replayed after a lost acquisition response; stop and investigate without automatic reconnects.
- Every application SDK GraphQL request and direct Admin HTTP request uses the shared resolver just before dispatch, including catalog pagination and long-lived workers. Existing tenant authorization still precedes this boundary; the resolver additionally matches exact shop/reference/current owner, rejects ambiguous owners, inactive integrations, deletion and uninstall/redaction.
- User SHARE locks serialize refresh with uninstall/reassignment; the pair UPDATE lock serializes per-store refresh across processes. It never takes a second privacy advisory lock, so it can run inside existing shop fences. Access+refresh replacement is atomic. One-minute maintenance handles **only already-migrated** due pairs, bounded to 50 per tick; no legacy conversion is reachable from cron/startup/resolver. Monitor aggregate failed counts and backlog as installation volume grows.
- 401 refresh failures mark the pair terminal without changing billing or deleting credentials. 429/5xx/transport failures preserve the durable pair. Configuration errors are bounded and require operator repair. Scope-denied 403 and the documented legacy-token rejection phrase remain distinct. No auth failure replays a mutation or customer send. Uninstall, erasure, shop/reference changes and account deletion purge encrypted credentials and pending migration intent through SQL triggers/FKs.
- `migrateAuthorizedLegacyInstallation` is an **operator library**, with no HTTP route, CLI, startup or cron registration. It requires exact owner/shop/client ID and an explicit invalidation acknowledgement. A durable non-secret intent fences legacy API use before the provider call. Failure retains the original legacy credential solely for authorized response recovery; success atomically installs the encrypted pair and clears intent. Concurrent operator invocations serialize under the existing shop privacy lock. No production invocation was performed.

## Review and controlled pilot sequence

1. Review code/CI first; review the additive SQL and production execution separately. Confirm the exact production app/client ID/public distribution, secret binding, pilot owner and `whachatcrm-live-test.myshopify.com`, grants and ownership. Inspect existing records and activity without printing credentials. Confirm all web/background workers will use the resolver; old workers must not remain after migration. Keep all WhatsApp/customer delivery gates OFF throughout.
2. After separately authorized schema/code release, provision a stable, independent 32-byte key in the secret manager for every web/worker replica. Verify key access, database role SELECT/INSERT/UPDATE permissions, encrypted backups/key recovery, both tables, cleanup trigger and cron readiness. Apply reviewed 0119 using the approved migration process/direct connection; do not use `db:push` or staging bootstrap. The generated schema alone is insufficient because it omits the cleanup trigger. Rehearse the actual migration on a disposable/schema-only environment first; never fork live credentials into active workers.
3. Obtain explicit authorization for **one exact store and production target** to invalidate its legacy token. Drain/pause that store's API work using an approved operational procedure, preserving webhook event ingestion/durable queues and all merchant data. Do not disable the integration, uninstall, reset billing, resubmit consent or alter global messaging flags. Record the authorized migration time externally. Confirm no old-process/API request remains in flight.
4. Invoke the reviewed operator library once for that exact owner/shop/client ID. Do not print inputs containing credentials, the pair, opaque reference or raw database/provider errors. Record only status and expiry metadata. On ambiguous/network/write failure, leave the durable intent in place; affected legacy calls fail closed and events remain durable. Recover the initial response only with the same original stored token within the seven-day eligibility window and before any newer acquisition/refresh. Stop on terminal/configuration errors or lost eligibility; no automatic reinstall, reconnect, legacy fallback, secret rotation or global batch.
5. Observe **two consecutive real pilot refreshes**, plus already-existing read-only webhook/scope/billing and catalog/order-sync health through normal runtime activity. Compare existing row counts/IDs, entitlements, trial dates, subscriptions, webhook registrations and message fences. Do not recreate orders/checkouts, send another YES/STOP, rebind templates or repeat historical live acceptance. New evidence must address token continuity only; do not bypass send/consent/outbox fences to obtain it.
6. Keep legacy stores untouched until pilot acceptance. Authorize each subsequent eligible store separately. Reconcile all workers and Dev Dashboard GraphQL/REST logs for remaining non-expiring token usage; the dashboard warning can lag its observation window. Keep #269 open until production evidence proves migration acceptance.

Rollback: stop further conversions. Before a store is migrated, legacy code/credentials remain usable. After migration, **never** roll back to code that treats the reference as a token or lacks refresh, and never restore a retired legacy pair from backup. Retain resolver-capable code, key and additive schema; forward-fix or use only the documented recovery path while preserving queues and existing merchant data. Removing the new key, tables or trigger after migration strands installations or violates erasure. A terminal refresh needs separately reviewed recovery; this PR does not force reconnects.
